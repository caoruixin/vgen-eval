## H3 推理架构与各阶段说明

本轮实际运行的是 H3-Base 的 768p 有声视频生成链路，使用 FL2VA 权重分区同时承接 T2VA 和仅首帧 FL2VA。官方完整产品体系另外包含 H3-Context-IR 输入理解与 H3-Regenerate-2K 再生成；本次自部署没有接入这两部分。原始中文 prompt 与首帧直接作为冻结输入，未增加提示词改写。官方 API 的内部预处理、推理步数与实现不可见，不能从本图推断其使用了哪些内部模块。

![架构图 A H3-Base 从冻结输入到有声 MP4 的推理链路](figures/h3-inference-flow.png)

### 输入处理和条件编码

请求先解析 task、prompt、画幅、时长、seed 与推理步数，并验证素材。T2VA 输入文本；本次 FL2VA 只提供 first_frame，未提供末帧。FL2VA 的名称描述模型支持的任务形式，不代表本轮同时使用了首尾帧。

H3-Encoder 采用 Qwen3-VL 编码文本及视觉语义，输出供生成模型使用的条件表示。首帧还经过 H3-VisualVAE 编码，形成保留画面结构的视觉 latent。两条路径分别提供语义和视觉条件，不能把图生视频简化成只把首帧放到最终视频开头。T2VA 没有这条首帧 VAE 编码路径。这里的 latent 是压缩后的内部表示，不是已经可以播放的帧或音轨。[模型架构说明](https://huggingface.co/MiniMaxAI/MiniMax-H3/blob/42ed227ee7df40d41602854ae760620d6eb651fe/README.md#model-architecture)

### 多模态联合去噪

运行时依据 seed 初始化视频和音频 latent 噪声，将文本条件、首帧条件和待生成的音视频 token 组织成多模态序列。H3-Omni-Transformer 在一次更新中同时预测视频和音频的变化，视频与音频调度器分别按各自 sigma 日程推进；首帧条件在循环中保留。音轨是模型联合生成的输出，并非在视频生成后另行调用 TTS 配音。联合生成提供音画协调的模型机制，实际口型、事件声音和台词同步仍须观看并听音验证。

50 步和 8 步指该去噪循环的更新次数，不是输出帧数，也不是把整个服务请求重复执行 50 次或 8 次。基线请求 50 步，日程包含 51 个 sigma 点，可归因串行日志观察到 50 次更新；六条 8 步试验均观察到 8 次更新。并发日志重叠时不逐请求归因计数器。固定实现使用蒸馏后的条件预测路径，不应照搬普通扩散模型“每步正负条件各跑一次”的计算假设。[固定版本去噪循环](https://github.com/vllm-project/vllm-omni/blob/5917730a4b02aedb44d374173cdc1b10484ccd52/vllm_omni/diffusion/models/minimax_h3/denoise_loop.py#L319-L455)

### 解码封装和结果检查

去噪结束后，H3-VisualVAE 将视频 latent 解码为像素帧，H3-AudioVAE 将音频 latent 解码为立体声波形，随后编码并封装成可下载的 MP4。本轮原片实际为 1344×768、24 fps、H.264 视频和 32 kHz 双声道 AAC 音轨。源实现同时提供完整解码和分块封装路径；本轮没有导出逐请求有效分支追踪，图中表示共同的逻辑流程，不把解码和封装画成已证实并行的耗时阶段。[固定版本推理管线](https://github.com/vllm-project/vllm-omni/blob/5917730a4b02aedb44d374173cdc1b10484ccd52/vllm_omni/diffusion/models/minimax_h3/pipeline_minimax_h3.py#L2201-L2300)

客户端完成下载后再运行 ffprobe、ffmpeg 全文件音视频解码和哈希核验。有效媒体不等于画质好、首帧保持好或音画同步正确；这些仍属于独立质量评审。上述校验耗时未计入本报告的主 E2E。

### 八卡如何参与一次生成

![架构图 B 本次 PRO6000 八卡配置与 rank 映射](figures/h3-gpu-layout.png)

文本编码器使用 TP8，把计算分到同一台机器的八张卡。生成主干采用 TP4 × Ulysses2 × Ring1，共八个 rank：TP4 的连续 rank 位于同一 NUMA 节点，Ulysses2 连接两个序列并行分组。TP 切分同一层的张量计算，Ulysses 切分较长的序列并交换 attention 所需信息，二者协作完成一次生成。视频 VAE 启用 tile 模式及 patch parallel size 8；实际并行工作量仍受瓦片数量及运行分支影响。

这些阶段复用同一组八张 GPU，不是文本编码、去噪、VAE 各占额外八张卡，也不表示同时生成八条视频。页面名称中的“PRO6000 ×8”表示硬件数量；C2、C4 才表示客户端同时存在两个、四个请求。C2/C4 的到达与完成时间只能支持观察窗口内吞吐，不能据此断言服务内部如何批处理或同时执行多个去噪循环。每张卡仍拥有独立的 96 GB 标称显存，不能当作单张 768 GB GPU。

图 B 反映已归档的启动参数、rank 规则和本机 NUMA 布局，未证明该映射最优，也未证明所有阶段八卡都达到相同利用率。后续 PRO5500 应沿用相同阶段定义，并单独记录该平台的拓扑、实际参数与测量结果。

### 阶段耗时能测到什么

![架构图 C 推理逻辑阶段与本轮耗时测量边界](figures/h3-timing-scope.png)

| 字段或阶段 | 本轮可以解释的内容 | 保留的限制 |
| --- | --- | --- |
| 客户端 E2E | 提交开始至 MP4 完整下载 | 自部署下载到推理服务器；官方 API 下载到笔记本，网络终点不同 |
| server_inference_time_s | 服务响应中返回的整体推理计时 | 不等同于独立 Transformer 去噪耗时 |
| queue_wait_ms | 入队至 Orchestrator 登记的间隔 | 不是全部调度排队；扩散调度器内部等待未在本轮 HTTP 响应中取得 |
| stage_0_gen_ms | vLLM Omni 服务阶段 0 的生成计时 | stage 0 包含管线工作，不能当成图 A 中某一个神经网络模块 |
| 编码器 去噪 VAE 封装各自耗时 | 本轮未取得可用独立计时 | 不相减推算，不按百分比分摊，也不把未填充的 0.0 当成实测零耗时 |

减少推理步数主要改变重复去噪工作，输入处理、条件编码、解码、封装和下载仍然存在，因此不能用 50÷8 直接宣称端到端加速 6.25 倍。本轮 8 步配置还改变了 video flow shift，Turbo 适配器文件已校验、实际激活未证实；现有结果只能描述“该 8 步配置观察到更短耗时”，不能分离步数、shift 与适配器各自的因果贡献。人工质量未锁定，也不能据此宣称同等质量的加速。

### 推理阶段与实验阶段的对应关系

上面的编码、去噪、解码属于一次请求内部的逻辑阶段。站点中的预热、基线、稳定性和并发则是组织多次请求的实验阶段；同步与异步描述 HTTP 交互方式，不代表音画同步水平。

| 实验阶段 | 请求配置与数量 | 主要观察目标 |
| --- | --- | --- |
| 预热 | 50 步；T2VA 和 FL2VA 各验证同步与异步；4 条有效，另 1 次输入拒绝 | 验证完整链路和接口，准备后续基线 |
| BF16 基线 | 50 步；同步；30 条 T2VA 与 12 条 FL2VA | 固定输入和多个 seed 下的标准性能 |
| 独立稳定性 | 50 步；异步；60 分钟，19 条有效，1 条窗口边界取消 | 持续运行和窗口内输出，不作长期 SLA 承诺 |
| 并发 C2 与 C4 | 50 步；异步；分别 2 条和 4 条有效 | 多请求到达后的交付耗时与整窗口吞吐 |
| 8 步配置试验 | 8 步；异步；T01 T04 T06 F01 F02 F03 各 1 条 | 观察另一配置，Turbo 激活未证实，质量待评 |
| 官方 API 对照 | 10 条有效；内部步数和硬件未知 | 相同冻结输入下的业务交付对照 |
